# 冒充高管/合作方邮件识别服务（BEC Detector）

在邮件送达员工之前，判断它是否在冒充公司内部人员或熟悉的合作方，并给出**可解释的中文判定依据**。
纯 Ruby 标准库实现，无第三方依赖，Ruby 2.6+ 可运行。

## 背景

财务部收到一封自称总经理的邮件，要求紧急支付并购定金，事后发现发件地址与真实地址只差一个字母。
这类攻击统称 BEC（Business Email Compromise），难点不在识别“垃圾内容”，而在：

1. **真高管也会用手机和私人邮箱发信** —— 不能把所有免费邮箱一棍子打死；
2. **合作方会换新邮箱** —— 未知域 ≠ 仿冒；
3. **攻击者可能真的盗用了合作方邮箱回复已有线程** —— 此时 SPF/DKIM/DMARC 全部通过，地址也是“熟人”；
4. **邮件文字本身完全正常** —— 不能依赖关键词黑名单，内容只能作为证据之一。

## 运行方式

```bash
rake test                 # 17 个单元测试
rake evaluate             # 309 封合成数据集评测，输出拦截率/误拦率
ruby bin/inspect.rb <发件地址> <显示名> <主题> <正文> [线程ID]   # 单封检测
ruby bin/mail_gateway.rb  # 原始 RFC822 邮件网关接入示例
```

## 评测结果（合成数据集 309 封：136 攻击 / 173 正常）

| 指标 | 数值 | 说明 |
|---|---|---|
| **攻击拦截率（直接 block）** | **62.5%**（85/136） | 仿冒域名、认证失败等确定性证据直接拦 |
| **综合处置率（block + 人工复核）** | **100%**（136/136） | 没有攻击邮件直接送达员工 |
| **硬误拦率（正常邮件被 block）** | **0%**（0/173） | 正常邮件零错杀 |
| **复核打扰率（正常邮件进人工队列）** | **2.89%**（5/173） | 全部是“系统确实不知道”的灰色邮件（见下） |

攻击邮件最低分 30、正常邮件最高分 41，两群在分数轴上不重叠，中间的灰色地带全部由**人工复核层**吸收——
这是刻意的设计：拿不准的邮件不拦死、也不放行，交给人确认。

### 为什么会有 2.89% 的复核打扰

5 封全部来自场景 B11：CEO 临时用一个**从未登记过的新私人邮箱**发信。
在系统视角里，它与攻击场景 A5（免费邮箱冒充高管）的特征几乎完全相同，任何自动化系统都无法区分，
正确做法就是复核一次，确认后把该别名加入员工 `known_emails`，以后自动放行。
这正说明“登记私人邮箱”这一管理动作的价值，而不是模型缺陷。

## 判断依据如何组合：证据加权 + 策略覆盖

### 五层证据模型

每封邮件产出一组带权重、带中文解释的证据，正分可疑、负分可信，代数求和：

| 层 | 信号举例 | 权重 |
|---|---|---|
| 身份层 | S01 仿冒公司域名（一字母之差/同形字/换后缀/子域滥用） | +38 |
| | S02 仿冒合作方域名 | +25 |
| | S03 免费邮箱冒充高管显示名且未登记 | +28 |
| | S07 未知域使用合作方显示名（疑似换邮箱） | +8 |
| 认证层 | S10 SPF/DKIM/DMARC 失败（每项） | +14 |
| | S11 Reply-To 与发件域不一致 | +12 |
| 线程层 | S12 陌生地址入侵已有往来线程 | +14 |
| | S13 回复旧线程却突然转向资金请求（话题突变） | +16 |
| 行为层 | S15 资金+紧急+保密的欺诈话术三元组 | +12 |
| | **S23 可信发件人突然要求变更收款账户且不提流程（被盗邮箱核心信号）** | **+32** |
| | S24 账户变更但有正式函/流程/确认表述（真实变更） | **−10** |
| | S25 低权限角色发出越权资金指令（角色偏离） | +12 |
| | S26 明确要求绕过审批（“不用走流程/事后补”） | +10 |
| 信任层 | S19 公司主域在册员工 / 登记过的私人邮箱别名 | −12 / −8 |
| | S20 合作方登记联系人 | −8 |
| | S21 地址在本线程历史中出现过 | −4 |
| | S22 地址在公司通讯录 | −3 |

### 分层处置阈值

```
score >= 55        → block       直接拦截，不进员工收件箱
30 <= score < 55   → quarantine  人工复核队列，复核员看到全部证据后放行或拉黑
score < 30         → allow       正常投递
```

### 策略覆盖规则（处理“分数会撒谎”的边界情况）

- **P1**：仿冒域名 + 资金语义 → 无视总分直接拦截（确定性证据）；
- **P2**：发件认证失败 + 资金/账户变更语义 → 直接拦截；
- **P3（难点1保护）**：登记过的高管私人邮箱即使分高也**永不直接拦截**，封顶降为复核，
  保证 CEO 用手机发的真邮件不会被拦死；
- **P4（难点2保护）**：合作方换域且无资金异常 → 只复核不拦截。

## 四个难点分别怎么解

**难点1：高管用手机/私人邮箱。** 员工档案里有 `known_emails` 别名表，
登记过的私人邮箱触发信任信号 S19（−8）并受 P3 保护；未登记的免费邮箱若使用高管显示名则触发 S03（+28）。
区分依据是“公司是否登记过”，而不是“是不是免费邮箱”。

**难点2：合作方换新邮箱。** 未知域只给基础低分（S07/S08，+8/+3），默认进复核而非拦截；
若新邮箱不谈资金、认证正常（场景 B4），分数甚至不到复核线，正常放行后由网关自动学习新域。
只有新邮箱同时发起资金/账户变更请求时才升级处置（攻击场景 A10 被 block）。

**难点3：合作方邮箱真的被盗、回复真实线程。** 此时域名、认证、地址、线程关系全部可信，
只能靠**行为基线**：
- S23：可信发件人突然通知收款账户变更，且没有正式函/流程/电话确认的措辞（+32）；
- S13：回复的是供货旧线程，话题却突变为付款（+16）；
- 对照真实变更（场景 B3）：出现“变更函、走流程、确认后生效”等表述 → S24 给 −10 分，直接放行。
同样的邮箱、同样的“账户变更”四个字，**措辞是否符合正常业务流程**成为分水岭。

**难点4：文字完全正常。** 内容语义（S15/S16）单项权重都很低（2~12 分），
永远无法单独触发拦截。拦截结论必须由身份层或行为层的硬证据支撑。
B10 场景里 CEO 从公司域谈并购付款还要求保密，信任分 −12 把语义分压下去，正常放行。

## 可解释性示例

```
$ ruby bin/inspect.rb 'ap@hongyuan-supply.com' '宏远供应商' '回复：供货合同' \
    '我司收款银行账户变更，请将款项尽快付至新账户' TH-HY-01

结论：🔶 人工复核（证据总分 34）
  [＋32] [行为层] 可信发件人突然通知收款账户变更且未提及任何变更流程/书面确认……
  [＋6 ] [行为层] 银行账户变更语义（命中：新账户、账户变更）
  [−8 ] [信任层] 发件地址是合作方“宏远供应商”的登记联系人邮箱
  [−4 ] [信任层] 发件地址在本线程的历史往来中出现过
```

复核员看到的不是一个黑盒分数，而是每条证据的方向、权重和触发原因，可直接据此电话核实。

## 生产化建议

1. **数据基线是上限**：`IdentityGraph` 应从 HR、邮件网关日志、CRM 自动同步，
   私人邮箱别名走员工自助登记 + 审批；
2. 真实环境用 `mail` gem 替换示例解析器，正确处理编码、别名地址和转发链；
3. 权重和阈值先用本仓库的标定方法在真实历史邮件（含已确认 BEC 事件）上重新标定，
   上线初期建议只开 quarantine，观察复核打扰率后再启用 block；
4. 语义层可替换为大模型判断，但保留证据加权框架——让模型输出结构化证据而非最终结论，
   可解释性和可调性都在框架这一侧；
5. 每次复核确认（放行/拉黑）回流为新的信任/可疑信号，形成闭环学习。
